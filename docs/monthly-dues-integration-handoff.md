## Action conflict and safety boundary

The three-way merge conflicts in `src/app/dashboard/uang-kas-bulanan/actions.ts`. The frontend branch currently has guarded read totals and deliberately fail-closed legacy register/payment actions; PR #25 contains actual register, member, payment, receipt and cash-book actions. PR #24 (`17b724f`) contains an older integration version of the backend actions. None may be blindly overwritten. Coordinate the resolution on the agreed integration path, keeping the backend implementations intact while enforcing a **server-side disabled feature gate** for payment, register/member writes and expenses until the owner approves integration QA. Hiding controls alone is insufficient: exported Server Actions can be invoked independently. Do not treat the frontend's existing fail-closed actions as a substitute for merging the backend implementation.

At the pinned backend reference `4211724`, `getMonthlyDuesPeriods` invokes lifecycle sync before reading, incompatible with read-only SSR/prefetch and the Secretary role. During this sprint PR #25 advanced to `3affab19`, which removes that call and makes the action read-only; its current CI must still complete and the updated commit must be reviewed as part of integration. Keep `lifecycle-sync-action.ts` as the separate, server-authorized command triggered after browser mount for Ketua Pemuda, Wakil Ketua Pemuda and Bendahara. Do not import the older page-load sync into generic read paths. Backend SQL `ensure_current_monthly_dues_period` additionally guards indirect rollover; frontend gates must not bypass it.

`monthly_dues_period_totals` is the source for all-period aggregate values. The separate `reference-check-action.ts` uses the existing `monthly_dues_summary.reference_amount` for exact head counts of all RLS-visible registers and those whose reference differs from Rp10,000, independent of pagination. It compares the register count to the totals view count and marks the result unavailable when inconsistent. The checks are separate read requests, not a transactionally consistent snapshot; backend and integration QA must validate grants/RLS, performance and behavior during concurrent changes. A matching total alone does not establish per-register consistency. Historical empty periods are not checked or manufactured.

## Future payment wiring — currently DISABLED

1. Only after backend approval and real integration QA, expose the actual backend payment Server Action with server authentication/authorization and validation. Preserve the database RPC `record_monthly_dues_payment(p_monthly_dues_id, p_amount, p_idempotency_key, p_note)`; never directly insert payment rows.
2. For a new intent, generate a cryptographically secure UUID and freeze actor, selected book, register UUID, exact decimal amount and normalized note. `payment-attempt.ts` is an isolated preparation helper, not an active payment integration. Persist the unresolved intent securely across a reload before any feature is enabled; the current helper alone does not do this.
3. Preserve precisely the same UUID and payload for every retry. On a timeout, transport failure or ambiguous commit, show **BELUM TERKONFIRMASI**, prevent a new intent, and reconcile by calling the **same RPC** with the same key and payload. Do not introduce a new key or infer failure. Backend reconciles a committed same-key request before the closed-period gate.
4. An explicit success requires a valid persisted transaction UUID returned by the RPC. Only then fetch the receipt from `monthly_dues_payment_receipts` by transaction ID/reference; preserve NULL name snapshots as unavailable. Receipt-fetch retry must never repeat the payment.
5. Backend's current payment action returns a generic error on any RPC failure and coerces the amount through `Number`, so it is not yet a safe ambiguous-outcome UI contract. Coordinate a typed error/outcome and exact decimal representation with the backend engineer before connecting it. Pay particular attention to `42501`/class `28` authorization, `22023` validation/key-payload conflict, `P0002` missing data, `55000` closed period, `40001` retryable conflict, and transport/timeout uncertainty; after a prior unknown outcome, a later rejection does not establish that the original failed.
6. Required QA includes commit-then-timeout, same-key concurrent commit and rollback, reload recovery, changed-payload rejection, after-close committed retry, roles, snapshots, fractional amounts, and real browser/Supabase end-to-end. Expense recording remains disabled independently.
