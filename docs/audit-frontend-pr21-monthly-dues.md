## Ketidaksesuaian dan pertanyaan untuk Backend Specialist/pemilik

1. **Kontrak belum final:** tipe `src/components/monthly-dues/backend-contract.ts` mencerminkan PR #22 lama (`2c00538...`), bukan jaminan kontrak akhir. Action `searchDuesMembers`, `ensureDuesRegister`, `createDuesMember`, respons transaksi dari `recordDuesPayment`, serta `getDuesPaymentReceipt` belum di-wire ke halaman.
2. **Status buka/tutup dan carry-forward:** kontrak draft `51cb2ed...` menyatakan saldo akhir bulan sebelumnya otomatis menjadi saldo awal berikutnya, dan view menggunakan `generate_series` hingga bulan berjalan/terakhir. Respons summary tidak memiliki status periode dibuka/ditutup. Keputusan bisnis terbaru menetapkan pembukaan eksplisit oleh pengurus dan saldo akhir periode sebelumnya sebagai saldo pembukaan periode berikutnya. Generate-series otomatis pada draft tidak membuktikan suatu periode telah dibuka dan bertentangan jika diperlakukan sebagai pembukaan otomatis. Backend final perlu menyediakan status otoritatif, aksi pembukaan eksplisit, saldo awal dari periode sebelumnya dan aturan validasi/penutupan yang diperlukan. Ini berbeda dari larangan membawa *kekurangan iuran* antarbulan.
3. **Model pembukuan:** frontend sementara mengusulkan `AccountingSnapshot`/`AccountingMutation` (`direction`, `complete`); PR #22 menawarkan `MonthlyDuesCashBookSummary` (`opening_balance`, `income_amount`, `expense_amount`, `closing_balance`) dan `MonthlyDuesCashMovement` (`movement_key`, `movement_type`, dst.), tanpa `complete` atau status penutupan. Jangan cast langsung. Utamakan angka summary otoritatif yang telah disetujui; definisikan pagination dan bukti kelengkapan untuk riwayat, dan jangan menghitung saldo dari halaman mutasi parsial. Hindari menjumlahkan `saldo_awal` kedua kalinya sebagai pemasukan.
4. **Akses:** frontend saat ini memasang panel historis statis untuk seluruh role dengan akses kas bulanan; PR #22 draft mensyaratkan `general_finance` untuk cash book/pengeluaran, sehingga Sekretaris dapat mengakses kas bulanan tetapi tidak cash book draft. Konfirmasi apakah label dan angka historis boleh terlihat pada role tersebut; data sensitif dan action final harus dibatasi di server sesuai keputusan final. Juga konfirmasi apakah saldo awal khusus kas dan snapshot keuangan umum berisiko menggandakan pelaporan.
5. **Potensi bug PR #22 draft:** pada `actions.ts` di commit `51cb2ed...`, regex `isOffsetTimestamp` memakai `\\\\d` dalam regex literal. Evaluasi ekspresi yang diambil dari file menghasilkan `false` untuk `2026-10-15T10:00:00+07:00`, sehingga tanggal ISO yang valid tampaknya ditolak. Ini temuan statis, bukan uji action/DB; perlu Backend Specialist memverifikasi dan memperbaiki jika masih ada di kontrak final. Frontend tidak mengubah file backend.
6. **Idempotensi dan status tak pasti:** action pembayaran existing mempertahankan key saat gagal; pengguna mengubah nominal/catatan lalu mencoba dengan key yang sama dapat terkena konflik payload. Menukar key secara otomatis setelah kegagalan tak pasti juga bisa menggandakan pembayaran. Perlu kontrak backend dan UX yang membedakan gagal pasti vs hasil tak diketahui sebelum perubahan retry. Gagal mengambil struk tidak boleh memicu ulang pembayaran.
7. **Tanggal/waktu dan identitas:** input `datetime-local` tidak membawa offset. Action pengeluaran draft meminta timestamp dengan offset dan periodenya harus sesuai Asia/Jakarta; cara konversi, verifikasi DST/timezone, dan idempotency key harus disepakati. Identitas pencatat harus berasal dari sesi server, bukan input pengguna.

## Update keputusan pemilik — persiapan pembukaan periode

Oktober 2026 adalah periode pertama dengan Rp205.000 historis, bukan pemasukan. November dan seterusnya hanya dibuka eksplisit oleh pengurus; saldo akhir sebelumnya menjadi saldo awal berikutnya, dengan saldo kas terakumulasi dan iuran/status anggota tetap bulanan. `PeriodPresentation` hanyalah boundary tampilan sementara: status `unopened`/`opened` dan total hanya ditampilkan jika data periode yang cocok diberikan. Halaman produksi belum memberikannya, sehingga status tetap **belum terverifikasi** dan angka tidak dikarang. Tombol pembukaan dinonaktifkan tanpa handler. Fixture test tidak membuktikan backend atau saldo sesungguhnya.

Backend final perlu menetapkan status buka otoritatif, izin, urutan periode, cara menentukan saldo akhir sumber, locking/idempotensi/concurrency pembukaan, rekonsiliasi transaksi terlambat, serta error dan batas data. Selaras aturan bisnis, jangan membuat periode kosong atau menyimpulkan status dari ketiadaan data. Verifikasi bahwa navigasi 12 bulan historis saat ini tidak menyediakan periode masa depan atau seluruh riwayat; integrasi perlu desain pilihan periode sesuai kontrak final, tanpa menciptakan record.

## Persiapan integrasi — kontrak terbaru PR #22 (`64e04901df28bdaa55b517f2ea4a55eb2fd510c5`)

PR #22 tetap draft; pemeriksaan CI pada commit ini lulus (test/typecheck/lint/build, migration chain lokal, Vercel). Migrasi belum diterapkan, riwayat migrasi hosted belum direkonsiliasi dan RLS/concurrency autentikasi belum diuji. PR #21 tidak berisi action atau skema baru ini; tipe di `backend-contract.ts` hanya cerminan untuk persiapan, bukan implementasi maupun kontrak final yang bisa dipanggil.

- `getMonthlyDuesPeriods()` → `{ periods: { dues_month, opened_at }[], error? }`; `openMonthlyDuesPeriod(duesMonth)` dan `generateMonthlyRegister(previous, formData)` (wajib `dues_month`) mengembalikan `DuesActionState`. Action register branch frontend saat ini tidak kompatibel dan dapat membentuk daftar bulan kalender tanpa pembukaan; UI tidak lagi menyajikannya. Sampai daftar resmi tersedia, layar fail-closed: tidak menampilkan periode atau memungkinkan pembayaran/pembukaan. Array periode kosong dari sumber resmi berbeda dari data yang belum tersedia/error; jangan mengubah error menjadi array kosong.
- `searchDuesMembers(query, duesMonth)` mengembalikan maksimum 15 anggota aktif berbasis UUID; `ensureDuesRegister(memberId, duesMonth)` dan `createDuesMember(fullName, duesMonth, confirmSameName?)` memerlukan periode dibuka. Konfirmasi nama sama sengaja dapat membuat anggota berbeda; UX perlu disambiguasi, jangan klaim nama unik. Search input dua sampai 80 karakter; error bukan hasil kosong.
- `recordDuesPayment(previous, FormData)` versi baru mengembalikan `transactionId`; `getDuesPaymentReceipt(transactionId)` membaca bukti persisten dan status saat transaksi. Implementasi branch ini masih versi lama dan tidak memberikan ID; struk masih tidak terhubung. Pertahankan retry baca bukti terpisah dari pembayaran.
- `getMonthlyDuesCashBook(duesMonth)` → `{ summary?, movements, error? }`; summary membawa `dues_month`, `opening_balance`, `income_amount`, `expense_amount`, `closing_balance`. Movement membawa `movement_key`, nullable `transaction_id`, `dues_month`, `occurred_at`, `movement_type`, `description`, `amount`, nullable `recorded_by` dan `note`, serta `immutable`. Ini bukan `AccountingSnapshot` dengan `complete`: jangan gunakan mutasi parsial untuk menghitung saldo. `recordMonthlyDuesCashExpense(previous, FormData)` memerlukan `dues_month`, `amount`, `description`, `spent_at` ber-offset dan `idempotency_key`. Regex timestamp di head ini sudah memakai escape yang benar; temuan regex pada SHA lama tidak boleh dianggap berlaku untuk head ini.
- Hak: daftar periode dapat dibaca per kebijakan draft oleh Ketua, Wakil, Bendahara dan Sekretaris; pembukaan khusus Ketua/Wakil/Bendahara; cash book dan pengeluaran memerlukan hak `general_finance`. Jangan memanggil cash book untuk role tanpa izin, dan jangan menyimpulkan saldo nol dari data yang dibatasi RLS.
- Risiko sebelum integrasi: hasil movements dan daftar periode tidak memiliki pagination/completeness; query `monthly_dues_summary` frontend lama terbatas 12 bulan serta mungkin dibatasi jumlah baris, sehingga tidak layak dipakai sebagai rekap lengkap semua periode; query tersebut sudah dihapus dari halaman fail-closed. Ringkasan backend menghitung carry-forward dari seluruh mutasi historis dan berubah jika transaksi historis berubah; sepakati implikasi ini, integritas RLS di semua tabel dan cara penanganan entri terlambat. Pembukaan atomik/urutan harus diuji secara concurrent pada DB terisolasi.
- Sesudah PR #22 tersedia pada branch dan migrasi telah disetujui/diterapkan di lingkungan uji: berikan hanya bulan dari respons sukses `getMonthlyDuesPeriods` ke `DuesDirectory`, muat agregat lengkap untuk daftar tersebut, hubungkan action final dengan otorisasi server, lalu uji loading/empty/error/sukses, retry aman, pagination dan role. `openedPeriods` saat ini hanya digunakan oleh fixture test dan tidak disuplai halaman produksi; tidak membuktikan integrasi end-to-end.

### Tindak lanjut audit halaman

Query agregat 12 bulan kalender, perhitungan bulan berjalan, dan input dummy ke directory tidak digunakan pada halaman. Guard izin baca tetap ada; halaman hanya menyatakan sumber periode belum terhubung, tanpa mengambil atau menampilkan periode maupun menyediakan pembayaran. Komponen directory dan fixture tetap merupakan persiapan terpisah, bukan bukti backend tersedia.
